# MAG-RAG: grounded question answering over metagenome annotation results

A small retrieval-augmented question-answering system over real results from a genome-resolved metagenomics study (two MAGs, bin.3 and maxbin.002; PlasticDB homology screening, eggNOG-mapper and InterProScan annotations). Answers are cited to protein IDs, aggregate questions are routed to an exact table tool instead of being guessed, and anything the data cannot support is refused rather than invented.

Built as a bioinformatics + applied-AI portfolio project. The RAG pattern (index, retrieve, answer with sources) follows the common learning path in [techwithprateek/agenticai-projects](https://github.com/techwithprateek/agenticai-projects); the code here is original and domain-specific.

## Motivation
Genome-resolved metagenomics produces many linked tables: homology hits, functional annotations, domain predictions and genome-quality metrics. Answering a simple question such as "which proteins in this MAG look like nylon-degrading enzymes, and how confident is that?" normally means joining several files by hand. This project asks how far a retrieval-augmented system can go on that task while staying scientifically honest: every answer is traceable to a protein ID, wording stays cautious ("putative", annotation-based), and questions the data cannot answer are refused instead of invented.

## Data and corpus
The source is a two-MAG study of a coastal sediment metagenome: **bin.3** (Desulfobacterota; GTDB-Tk placement JAENJC01; 100% complete, 1.01% contamination) and **maxbin.002** (Chloroflexota, Anaerolineae; 86.75% complete, 7.64% contamination). Plastic-degradation candidates were screened with DIAMOND against **PlasticDB** (329 curated proteins) and tiered by identity, coverage and e-value (Tier 1 strong, Tier 2 moderate, Tier 3 remote). Annotations come from eggNOG-mapper; Pfam/InterPro domains come from InterProScan (run on the 31 Tier 1 and Tier 2 proteins).

The retrieval corpus has **79 documents**:
- 76 protein cards, one per protein with a PlasticDB hit, each combining the homology hit (enzyme, polymer, source organism, identity, coverage, e-value, tier), the eggNOG annotation (description, KO, COG, EC, Pfam) and InterProScan domains where available;
- 2 MAG cards (taxonomy, completeness, contamination, size, coverage, annotation counts);
- 1 method card (how the tiers are defined).

All values are read from the project's own result tables by `src/build_corpus.py`; nothing is generated by a language model.

## How it works
```
question
  1. guardrails      unsupported claims (experimentally validated, kinetics, pH optimum...) -> refuse
                     protein IDs that are not in the corpus -> refuse
  2. router          "how many ..." + filters (MAG / tier / polymer) -> exact pandas count
                     "which proteins ..." + filters                  -> exact pandas list
  3. retrieval       everything else: BM25 + TF-IDF (+ MiniLM dense embeddings, optional),
                     fused with reciprocal-rank fusion; questions containing an exact
                     protein ID use lexical-only retrieval
  4. answer          cited, extractive answer built from the retrieved cards
                     (weak lexical match -> "Not available in current project outputs.")
```
Why a router? Retrieval is poor at counting and at exhaustive lists, so those questions go to the table itself. Why lexical-only for IDs? Dense embeddings do not understand locus tags (see the evaluation).


## Design decisions
- **No generated facts.** The answer is assembled from retrieved cards; an LLM rewrite step could be added on top of the same evidence but is deliberately not part of the evaluated system.
- **Refusal is a feature.** A corpus of homology hits cannot say anything about enzyme activity, so the system says so.
- **Exact tools for exact questions.** Counting and listing are not retrieval problems.
- **Honest evaluation.** Gold answers are computed from the tables, and the README reports weak results next to strong ones.

## Usage
```bash
pip install -r requirements.txt      # add sentence-transformers for dense retrieval
python src/build_corpus.py /path/to/mag_reconstruction   # builds data/corpus.jsonl from the project tables
python src/ask.py "What is ADACJJMH_01622 annotated as?"
python src/ask.py "How many Tier 1 PlasticDB hits does maxbin.002 have?"
python src/eval.py                                       # writes outputs/eval_results.csv
```

## Evaluation
Questions are generated from the tables with computed gold answers (seeded, `src/eval.py`); 91 questions in total. Retrieval systems compared on the three search tasks (Hit@1 / Hit@3):

| System | ID lookup (n=30) | Description search (n=20) | Pfam domain search (n=11) |
|---|---|---|---|
| BM25 | 1.00 / 1.00 | 0.75 / 0.95 | 0.27 / 0.55 |
| TF-IDF | 1.00 / 1.00 | 0.80 / 1.00 | 0.27 / 0.73 |
| Hybrid (BM25+TF-IDF) | 1.00 / 1.00 | 0.80 / 0.95 | 0.27 / 0.55 |
| Dense only (MiniLM-L6-v2) | 0.03 / 0.07 | 0.45 / 0.70 | 0.18 / 0.27 |
| Hybrid + dense | 0.23 / 0.63 | 0.65 / 1.00 | 0.64 / 0.73 |
| **Full pipeline** (dense only for non-ID queries) | 1.00 / 1.00 | 0.65 / 1.00 | 0.55 / 0.55 |

Other tasks (full pipeline): count questions 6/6, list questions 14/14, unanswerable questions refused 10/10.

**Takeaways:** dense embeddings alone fail on exact identifiers (3% hit@1 on IDs) because MiniLM does not understand locus tags; fusing them with lexical search helps the domain-search task (0.27 to 0.64 hit@1) but hurts ID lookup, so the pipeline routes ID questions to lexical-only retrieval. On description search the lexical hybrid has the best hit@1 (0.80 vs 0.65), so the routed pipeline trades top-1 precision for recall at 3 there.

## Limitations (please read)
- **Small, templated evaluation.** Questions are generated from templates over one dataset; sample sizes are small (domain search n = 11). ID lookup is easy for lexical retrieval by construction.
- **Tool and refusal scores are not retrieval quality.** Count and list results test routing and parsing against exact tables; the refusal set uses rules I wrote alongside the test questions, so 10/10 is optimistic.
- **Pfam domain search is still the weak spot** (best hit@3 is 0.73). Domain search has only 11 questions, so differences between systems are not statistically reliable.
- The question templates, the refusal rules and the router regexes were written by the same person (me), so the tool and refusal scores in particular will not transfer to free-form user questions.
- Corpus covers only proteins with a PlasticDB hit and the two MAGs; it cannot answer questions about the rest of the genome.
- Underlying biology is annotation-based: homology hits are putative candidates, not evidence of enzymatic activity.

## Possible next steps
- Evaluate on free-form questions written independently of the rules, and with a real LLM rewrite step (OpenAI or Ollama) while measuring hallucination against the cited cards.
- Add literature abstracts on plastic-degrading enzymes as a second corpus, with a separation between "this study's data" and "published evidence".
- Replace the Pfam/InterPro text matching with structured domain filters, and index a protein-language-model embedding of the sequences themselves.
- Extend the corpus from the PlasticDB-hit proteins to all annotated proteins of both MAGs.
